# Adopt an existing speaker over SSH

The intended experience is to connect an existing supported speaker to a new Home Assistant installation when the owner knows nothing about its previous intercom installation. No backup, previous Home Assistant, old intercom identity, or manual restore is a prerequisite. This document records the intended workflow. See ADOPTION-DEVELOPMENT.md for the implemented, restricted 0.5.0b1 candidate and its validation limits.

1. In the Home Assistant GUI, choose **Adopt existing speaker**. Provide a reachable address and root SSH password. Discovery may help find an address, but a password alone cannot identify a network destination. For an unknown SSH host key, display its fingerprint and require the owner to verify it through an independent trusted channel before sending the password. Do not automatically trust a changed key. A VPN can provide the route; it does not by itself authenticate the SSH host.
2. Read fixed, bounded metadata over SSH. Verify supported model and architecture; identify the running or stopped application, the installed app and startup hashes, the transaction journal, current native connections, and device state. Never print credentials or private key material. Explain whether the device is supported. Unknown firmware, a pending transaction, conflicting active calls, insufficient storage, or an unsafe filesystem state must stop adoption with a specific reason rather than being classified as stock or overwritten.
3. Show the owner the detected device and explain that adoption replaces its current intercom identity and may interrupt its existing voice service. Confirm the intended device and action. The new Home Assistant creates its own paired credentials. No old credentials or old Home Assistant backup are needed.
4. Adopt through a purpose-built, bounded transaction. Bind it to the verified SSH host key, physical device identity, observed files and current state; recheck them immediately before writing. Use a fixed package and preserve authentication, clock freshness, transaction journaling and uncertain-result reconciliation. The transaction must handle a stopped application and an existing unmanaged intercom installation without pretending they are stock. It must not depend on an unavailable previous HA identity. Retaining a temporary on-device recovery snapshot is an implementation detail, not an input the owner must supply; if safe recovery cannot be established, return an actionable failure instead of claiming success.
5. Verify the installed application and configuration, start it using fresh Home Assistant clock authority, establish authenticated native TLS, and only then create the speaker profile and room. Give selected users explicit room access. Report the room's name and actual connection state.
6. Guide a person at the speaker through a bounded two-way audio, mute, indicator, unmute and hangup test. Separately verify restart and interruption recovery. Never treat SSH connectivity or a software counter as proof that sound or privacy indicators work.

## What must be built

Version 0.4.10 does not implement this workflow. Its SSH connection requires an independently verified host key and known device identifiers; its install path rejects an unmanaged existing installation, rejects a stopped application as an install baseline, and requires an action-bound physical checkpoint. The firmware transaction also expects clock and recovery attestations. A working adoption feature needs a reviewed change across the HA options flow, fixed SSH transport and discovery, deployment state machine, device transaction and GUI. It also needs tests for host-key mismatch, interrupted transfers, changed state, unknown builds, stopped processes, duplicate adoption, privacy, and restart/recovery on a real development speaker.

Do not generate false test attestations or remove the checks as a shortcut. The implementation should fail clearly on unsupported states and make no claim that it can recover an arbitrary unknown build until that state has actually been tested.
